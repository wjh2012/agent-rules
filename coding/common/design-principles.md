# 설계 원칙 (언어·프레임워크 무관)

## 판단 기준

- **아키텍처·도메인 로직 우선**: 설계 판단 시 컨트롤러 변경 최소화 같은 편의성보다
  아키텍처 정합성과 도메인 로직의 올바름, best practice를 우선한다.
- **가독성 우선**: 코드는 이해하기 쉬워야 한다. 암묵적인 로직보다 명시적인 구현을 선호한다.

## 상태 변경은 의도를 드러내는 메서드로

Setter 로 필드를 열지 않는다. 무엇을 바꾸는지가 아니라 **왜 바꾸는지**가 메서드 이름에
드러나야 한다. `setStatus(DONE)` 대신 `complete()` 를 쓴다.

호출부만 읽고도 도메인 규칙을 알 수 있고, 상태 전이 조건을 한곳에서 검증할 수 있다.

> 구현: [spring-java/entity.md](../spring-java/entity.md)

## 느린 I/O 는 트랜잭션 밖에서

**파일 I/O·외부 API 호출은 DB 트랜잭션 밖에서 수행한다.**

파일 저장·읽기는 디스크 또는 네트워크 I/O 라 수백 ms~수 초가 걸린다. 그동안 트랜잭션이
열려 있으면 DB 커넥션이 아무 일도 하지 않고 점유된다. 커넥션 풀이 고갈되면 그 API 하나가
아니라 전체가 대기 상태가 된다.

트랜잭션은 DB 작업만 감싸고, 느린 I/O 는 그 앞뒤로 뺀다.
