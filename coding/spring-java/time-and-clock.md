# 시간 컬럼의 시계 소유 — Java · Spring

> **불변식: 하나의 시간 컬럼은 쓰기와 비교가 같은 시계를 쓴다.**
>
> 어기면 두 시계의 편차가 그대로 판정 오차가 된다. 컴파일도 되고 테스트도 통과하며,
> 편차가 임계값을 넘는 날에만 조용히 오작동한다.

## 시계는 컬럼이 소유한다

시계는 잡·서비스가 고르는 것이 아니다. **어떤 컬럼을 비교 축으로 쓸지 정해지면 시계도 따라서
정해진다.** 새 배치를 만들 때는 판정 축 컬럼을 먼저 정하고 그 컬럼의 시계를 따라간다.

| 컬럼 부류 | 소유 시계 | 이유 |
|---|---|---|
| 감사 컬럼 (등록·변경 일시) | **앱 시계** | 한 호스트가 쓰고 사람이 읽는 기록값이다. 호스트 간 편차는 표시 오차로 끝난다. 앱에서 만들면 객체와 DB 행이 같은 값을 갖고, 테스트에서 시계를 고정할 수 있다 |
| 호스트 간 판정용 컬럼 (하트비트 등) | **DB 시계** | 한 호스트가 쓰고 다른 호스트가 판정한다. 두 시계가 어긋난 만큼이 그대로 오판정이 되고, 그 결과가 파괴적이면 되돌릴 수 없다. DB 시계로 통일하면 편차 항이 0 이 된다 |

## 앱 시계는 주입받는다

`LocalDateTime.now()` 를 그대로 호출하지 않고 `Clock` 빈을 주입받아 `now(clock)` 으로 쓴다.
테스트에서 시계를 고정해 경계값을 정확히 검증하기 위해서다.

## 감사 컬럼 값을 SQL 에서 만들지 않는다

DB 함수로 감사 일시를 만들면 **애플리케이션 객체는 그 값을 모른다.** 등록 응답은 `null` 이 되고,
수정 응답에는 **갱신 전 옛 값**이 실린다. 뒤쪽이 특히 위험하다 — 값이 그럴듯해서 테스트로도
잘 잡히지 않는다.

인터셉터가 SQL 실행 **전에** 파라미터 객체의 필드를 채우면, 호출부는 저장 직후 그 인스턴스에서
값을 바로 읽을 수 있다.

**인터셉터가 걸리지 않는 경로**(파라미터가 단일 엔티티가 아니라 맵으로 감싸지는 다중 파라미터
문 등)에서는 감사 컬럼을 매퍼에 직접 명시한다. 매퍼만 보고는 인터셉터가 걸리는지 알 수 없으므로
리뷰 체크 항목으로 둔다.

## 근거를 주석에 남긴다

시계 선택은 **양쪽 다 그럴듯해 보이는** 결정이라, 근거가 없으면 다음 사람이 반대로 되돌린다.
시계를 고른 지점에 **불변식과 판정 축을 함께** 적는다.

"호스트 시계 편차 방지" 같은 시나리오만 적으면 반대편 배치에도 똑같이 들어맞아 근거 구실을
못 한다.
