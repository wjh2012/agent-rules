# agent-rules

LLM·코딩 에이전트에게 주는 규칙 모음. 프로젝트마다 다시 쓰지 않으려고 한곳에 모은다.

각 프로젝트는 여기서 필요한 규칙을 골라 자기 `rules/` 또는 `docs/rules/` 아래로 내려 쓴다.

## 구조

```
writing/
  rules/                 국문 문체 규칙 (문서 종류 무관)
  references/            규칙의 근거가 되는 배경 자료 (규칙 아님)

coding/
  common/                언어·프레임워크 무관
  spring-java/           Java · Spring 스택
    mybatis/             MyBatis 전용 (JPA 프로젝트에는 적용하지 않는다)
  skills/                Claude Code 스킬
  agents/                서브에이전트
```

## 넣는 것 / 안 넣는 것

**넣는다**
- 여러 프로젝트에서 재사용되는 규칙
- 플레이스홀더(`{project}`, `{도메인}`)나 가상 예시로 설명되는 규칙
- 규칙의 근거가 되는 배경 자료 (`references/` 아래)

**안 넣는다**
- 특정 코드베이스에만 존재하는 클래스·설정을 전제한 규칙
- 조직 보안 정책처럼 다른 프로젝트에 퍼지면 해로운 제약
- 특정 프로젝트의 분석·TODO·벤치마크 문서
- 개인 정보, 실제 회사·프로젝트 이름

애매하면 **"다른 프로젝트에서 이 파일을 그대로 가져다 쓸 수 있는가"** 로 가른다.
못 쓰면 그 프로젝트의 `rules/` 에 둔다.

## 프로젝트에 설치할 때

1. 필요한 규칙 파일을 프로젝트의 `docs/rules/` 로 복사한다.
   `coding/skills/` 의 스킬들이 `docs/rules/{이름}.md` 를 직접 읽으므로 파일명을 바꾸지 않는다.
2. 스킬은 `.claude/skills/`, 에이전트는 `.claude/agents/` 로 복사한다.
3. 프로젝트 `CLAUDE.md` 에 아래를 적는다.
   - **바인딩**: 공통 베이스 예외·전역 핸들러·응답 래퍼·파일 진입점의 실제 클래스명
   - **스킬 매핑**: 어떤 요청에 어떤 스킬을 쓰는지 (안 적으면 스킬이 호출되지 않는다)
   - **HTTP 메서드 정책**: 허용 메서드와 CUD 경로 패턴

## 파생본

프로젝트로 내려간 규칙은 **그 프로젝트가 정본**이다. 프로젝트별 결정이 덧붙기 때문에
여기로 되돌려 합치지 않는다. 한쪽만 고치면 되도록 방향을 한 방향으로 고정한다.

| 규칙 | 파생본 | 그 문서를 쓸 때의 정본 |
|---|---|---|
| `writing/rules/문체.md` · `문체_검사.md` | RESUME `rules/문체.md` · `rules/문체_검사.md` | RESUME 쪽 |

RESUME 쪽에는 여기 없는 것이 붙어 있다 — 이력서 문서별 규칙(`rules/문체_문서별.md`),
반복 지적받은 표현 목록, 개인 결정 이력. 전부 그 저장소에서만 쓰는 것이라 여기로 올리지 않는다.

**예외** — 규칙 자체의 구조 변경이나 결함 수정은 역방향으로 가져온다. 규칙 번호 체계(B1~B8),
잘못된 예시, 오탐 내는 정규식은 어느 프로젝트에서 고쳤든 공통이기 때문이다. 옮기지 않는 것은
내용이지 구조가 아니다.
