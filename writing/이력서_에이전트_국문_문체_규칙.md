# 국문 이력서 작성 에이전트 — 문체 규칙

> 대상 문서: 경력기술서(개조식) / 자기소개서(서술형)
> 용도: 시스템 프롬프트 규칙 + 후처리 린트 패턴
>
> **파생본 주의**: 이 규칙은 개인 이력서 저장소(RESUME)의 `rules/문체.md` ·
> `rules/문체_문서별.md` · `rules/문체_검사.md` 로 흡수되어 있다.
> **이력서를 쓸 때는 그쪽이 정본**이고, 그쪽에는 여기 없는 개인 결정 사항이 들어 있다.
> 이 파일은 다른 프로젝트에서 재사용할 범용 원본이다.

---

## 0. 문서 유형별 문체 대조

두 문서는 **문체 규칙이 상당 부분 정반대**다. 에이전트는 생성 전에 반드시 문서 유형을 먼저 확정해야 한다.

| 구분 | 경력기술서 | 자기소개서 |
|------|-----------|-----------|
| 기본 문체 | 개조식 (명사형 종결) | 서술형 (완결 문장) |
| 종결 | `~ 구축`, `~ 개선`, `~ 도입` | `~했습니다`, `~합니다` |
| 주어 | 대부분 생략 | 필요 시 "저는" (최소한으로) |
| 1인칭 | 사용 안 함 | 제한적 사용 |
| 문장 길이 | 1~2줄 | 2~4문장 단위 |
| 핵심 | 사실·수치·기술 스택 | 동기·과정·판단·성장 |
| 시제 | 과거 사실 중심 (명사형이라 시제 표시 약함) | 과거형 서술 + 현재형 마무리 |
| 감정 표현 | 배제 | 제한적 허용 |

## 1. 공통 규칙 (두 문서 모두 적용)

### R1. 능동태 우선 — 수동태 금지

기여 주체가 드러나야 한다. 수동태는 누가 했는지를 숨긴다.

| ❌ | ✅ |
|---|---|
| 응답 속도가 개선되었습니다 | 쿼리 인덱스를 재설계해 응답 속도를 40% 단축 |
| 배포 프로세스가 자동화됨 | GitHub Actions 기반 배포 파이프라인 구축 |
| 장애가 해결되었습니다 | 커넥션 풀 설정을 조정해 장애를 해결했습니다 |

**금지 표현**: `~에 의해`, `~되어지다`, `~지게 되었다`

---

### R2. 헤징(완곡·추측) 금지

일상 한국어의 완곡어법은 이력서에서 성과를 약화시킨다. 단정적으로 쓴다.

| ❌ | ✅ |
|---|---|
| ~에 기여한 부분이 있습니다 | ~을 주도해 ~을 달성했습니다 |
| 어느 정도 개선된 것 같습니다 | 30% 개선했습니다 |
| 도움이 되었다고 생각합니다 | (삭제하고 결과 수치로 대체) |
| 참여하였습니다 | 설계·구현했습니다 / (역할 명시) |

**금지 표현**: `것 같습니다`, `생각됩니다`, `~한 편입니다`, `나름`, `조금이나마`, `어느 정도`

> **예외**: 진행 중이거나 검증되지 않은 성과는 과장 대신 범위를 명시한다.
> "약 30% 개선(사내 부하 테스트 기준)"

---

### R3. 수치·근거 필수

정성 표현은 정량 지표로 치환한다. 지표가 없으면 규모·범위·기간으로 대체한다.

| ❌ | ✅ |
|---|---|
| 대규모 트래픽 처리 | 일 평균 200만 요청 처리 |
| 성능을 크게 개선 | p95 응답시간 1.2s → 320ms |
| 여러 서비스 개발 | 사내 3개 서비스의 인증 모듈 통합 |
| 팀을 이끌었습니다 | 백엔드 4인 팀의 기술 리드를 맡았습니다 |

**정량화 축**: 비율(%) / 절대값 / 시간 / 규모(사용자·트래픽·데이터) / 인원 / 비용

---

### R4. 명사 반복 허용, 대명사·동의어 치환 금지

"그것", "해당", "이러한" 남발은 지시 대상을 모호하게 만든다. 고유명사를 반복하는 편이 명확하다.

| ❌ | ✅ |
|---|---|
| 결제 시스템을 개편했습니다. 그것은 안정성을 높였습니다. | 결제 시스템을 개편해 결제 실패율을 2.1% → 0.3%로 낮췄습니다. |
| 해당 프로젝트에서 이러한 부분을 담당 | 정산 배치 파이프라인의 스케줄링 로직 담당 |

**주의 표현**: `해당`, `이러한`, `그것`, `동 프로젝트`, `상기`

---

### R4-1. 같은 문장 안에서 재지칭할 때는 선행어와 명사를 일치시킨다

지시관형사(`그`, `이`) 자체는 R4 위반이 아니다. 문제는 **앞에서 가리킨 대상을 뒤에서
다른 명사로 바꿔 다시 지칭**하는 경우다 — 독자가 두 표현이 같은 대상인지 재확인해야 한다.

```
❌ 하나가 실패해도 그 단위만 다시 처리합니다.
   (앞: "하나" / 뒤: "단위" — 같은 대상을 다른 말로 가리킴)
△ 한 단위가 실패해도 그 단위만 다시 처리합니다.
   (명사는 맞췄지만 "단위"가 두 번 반복되며 지시어가 그대로 남아 늘어짐)
✅ 실패한 단위만 다시 처리합니다.
```

가장 자연스러운 해법은 **지시어 자체를 없애고 관형절로 합치는 것**이다("~한 단위만").
선행 명사만 맞추는 안(△)은 R4-1 위반은 벗어나지만 반복이 남아 차선책에 그친다.

### R6. 날짜·표기 형식 통일

- 기간: `2023.03 ~ 2025.06` (년-월 순, 큰 단위 → 작은 단위)
- 재직 중: `2025.07 ~ 현재`
- 기술 스택: 공식 표기 그대로 (`PostgreSQL`, `Kubernetes`, `Node.js`)
- 숫자: 천 단위 콤마, 비율은 `%` 밀착 (`40%`)
- 영문 약어 첫 등장 시 풀네임 병기 후 이후 약어 (`CI/CD(지속적 통합·배포)`)

### R7. "진행/수행/담당" 같은 무색 동사 지양

무엇을 했는지가 드러나지 않는다. 구체 동사로 교체한다.

| 무색 동사 | 대체 동사 예시 |
|---|---|
| 진행 / 수행 | 설계, 구현, 배포, 마이그레이션, 리팩터링, 튜닝 |
| 담당 | 주도, 설계, 운영, 개선, 자동화 |
| 참여 | (역할 명시) 구현, 리뷰, 아키텍처 설계 |

### R8. 한 문장 안에서 숨은 주어를 바꾸지 않는다 ★

**LLM이 생성한 한국어에서 가장 흔한 어색함의 원인.** 한국어는 주어를 생략하므로,
절마다 숨은 주어가 달라지면 읽는 사람이 매번 주어를 다시 추론해야 한다.

#### 문제 사례

```
❌ 작업은 개별 단위로 나눠, 실패하면 그 단위만 재시도합니다.
```

| 절 | 숨은 주어 |
|---|---|
| 작업은 개별 단위로 **나눠** | 나(개발자) |
| **실패하면** | 작업 / 단위 |
| 그 단위만 **재시도합니다** | 시스템 또는 나 |

`작업은`을 주제로 던진 직후 능동 타동사 `나눠`가 붙어, 순간 "작업이 무언가를
나눈다"로 읽힌다. 문법 오류는 아니지만 판독 부하가 크다.

```
❌ 엔진은 특정 업무에 묶이지 않게 분리해, 소스 획득 방식이 달라져도
   같은 구조를 재사용합니다.
```
→ 주어가 **4번** 바뀐다. (나 → 엔진 → 소스 획득 방식 → 나)
→ 게다가 `묶이지 않게`(피동)와 `분리해`(능동)가 한 절에 섞여 있다.

#### 핵심 원칙

> **사물을 주어로 둘 거면 서술어를 상태·피동으로,**
> **행동을 서술할 거면 목적어로 내리고 주어를 행위자로 통일한다.**

둘을 섞으면 안 된다. `엔진은 ... 분리해`는 이 규칙 위반이다.

| 선택 | 형태 | 예시 |
|---|---|---|
| 상태 서술 | `A는 ... 되어 있다` | 엔진은 업무 로직과 분리되어 있습니다 |
| 행동 서술 | `A를 ... 했다` | 엔진을 업무 로직과 분리했습니다 |

#### 수정 예시

**방식 A — 주어를 행위자(나)로 통일**
```
✅ 여러 워커가 대기열에서 작업을 꺼내 변환하는 비동기 구조를 설계했습니다.
   작업을 개별 단위로 쪼개 두어 실패한 단위만 다시 처리하면 됩니다.
   변환 엔진은 특정 업무에 종속되지 않도록 분리했기 때문에, 소스를
   압축파일·단일파일·원격 중 어디서 가져오든 같은 엔진을 그대로 씁니다.
```
→ 첫 문장에 R10-1을 적용해 "이미지 변환을 ... 설계했습니다" + "워커 프로세스가
   ... 처리합니다" 두 문장을 하나로 응축했다.

**방식 B — 사물 주어 + 상태 서술로 통일**
```
✅ 이미지 변환은 여러 워커 프로세스가 대기열에서 꺼내 처리하는 비동기
   구조입니다. 작업은 개별 단위로 쪼개져 있어, 실패한 단위만 다시 처리됩니다.
   변환 엔진은 특정 업무와 분리되어 있어, 소스 획득 방식이
   압축파일이든 단일파일이든 원격이든 같은 구조로 동작합니다.
```

> 두 방식 중 하나를 **문단 단위로 일관되게** 적용한다. 문단 안에서 A와 B를
> 섞으면 같은 문제가 반복된다.

#### 부속 규칙: R1(능동태)과의 충돌 조정

R1은 능동태를 요구하지만, **사물이 주어일 때는 상태·피동 서술이 오히려 옳다.**
두 규칙의 적용 기준은 다음과 같다.

| 서술 대상 | 적용 규칙 |
|---|---|
| 내가 한 행동·기여 | R1 우선 — 반드시 능동 (`~을 설계했습니다`) |
| 시스템의 구조·상태 | R8 우선 — 상태 서술 허용 (`~로 분리되어 있습니다`) |
| 성과 지표의 변화 | 상태 서술 자연스러움 (`응답시간이 320ms로 줄었습니다`) |

핵심은 **기여를 숨기는 수동태**(R1이 막으려는 것)와 **구조를 설명하는 상태
서술**(R8이 허용하는 것)을 구분하는 것이다.

```
❌ 배포 프로세스가 자동화되었습니다        → 기여 은폐. R1 위반
✅ 배포 파이프라인을 구축했습니다           → 행동 서술
✅ 배포는 머지 시점에 자동 트리거됩니다     → 구조 설명. 허용
```

### R9. 쉼표 연결(`-해,` `-며,`)을 한 문장에 2회 이상 쓰지 않는다

영어 분사구문을 직역한 리듬이다. 연결어미로 계속 이어붙이면 문장이 늘어지고
R8의 주어 전환 문제가 함께 발생한다.

```
❌ 엔진을 분리해, 방식이 달라져도 재사용하며, 실패 시 재시도합니다.
✅ 엔진을 업무 로직과 분리했습니다. 덕분에 소스 획득 방식이 달라져도 같은
   엔진을 재사용합니다.
```

- 쉼표 연결이 2회를 넘으면 문장을 끊는다.
- 인과 관계는 `-해,` 대신 `~했기 때문에`, `덕분에`, `그 결과` 로 명시한다.
- 자기소개서 기준 **한 문장 60자 내외**를 권장한다.

### R10. Garden path 문장을 만들지 않는다

문두 성분이 뒤늦게 다른 서술어에 걸리면, 독자가 문장을 중간에 다시 읽는다.

```
❌ 이미지 변환을 여러 워커 프로세스가 대기열에서 꺼내 처리하는 비동기
   구조로 설계했습니다.
```
→ `이미지 변환을`이 처음엔 `설계했습니다`의 목적어로 읽히다가, 끝에 가서야
   `처리하는`의 목적어였음이 드러난다.

```
△ 이미지 변환을 비동기 구조로 설계했습니다. 여러 워커 프로세스가 대기열에서
   작업을 꺼내 처리합니다.
```
→ 문장을 나눠 Garden path는 피했지만 새 문제가 생긴다. "이미지 변환"(동작
   명사)이 "구조로 설계했다"의 목적어 자리에 앉으면서 목적어-서술어 궁합이
   어긋나고, 두 문장을 이어줄 장치가 없어 뒷문장이 앞문장의 무엇을
   구체화하는지 독자가 추론해야 한다. R10-1을 우선 적용한다.

**점검 방법**: 목적어와 그것을 받는 서술어 사이에 10어절 이상이 끼어 있으면
문장을 분리한다. 단, 원인이 R10-1 패턴(동작 명사가 구조/시스템과 잘못
결합)이면 분리 대신 R10-1의 관형절 기법을 먼저 시도한다.

---

### R10-1. 동작 명사를 상위 개념과 바로 묶지 않는다 — 관형절로 내재화

"OO을 구조/시스템/파이프라인으로 설계·구축했다" 꼴에서 OO이 동작을 명사화한
말(변환·처리·전송·검증·응답·저장 등)이면, 목적어(동작)와 서술어(설계하다)의
범주가 어긋나 어색하다. **실제 설계 대상(구조·시스템·파이프라인)을 목적어로
세우고, 동작 명사는 관형사형 어미(`~하는`)로 바꿔 그 대상을 꾸미는 관형절
서술어로 내린다.**

```
❌ 이미지 변환을 비동기 구조로 설계했습니다. 여러 워커 프로세스가 대기열에서
   작업을 꺼내 처리합니다.
✅ 여러 워커가 대기열에서 작업을 꺼내 변환하는 비동기 구조를 설계했습니다.
```

| 원래 문제 | 해소 방식 |
|---|---|
| 목적어(동작 명사)-서술어(설계하다) 범주 불일치 | 목적어를 구조·시스템 등 실체 명사로 교체 |
| 문장 간 연결 장치 없음 (뒷문장이 앞문장 무엇의 구체화인지 불명) | 한 문장으로 응축, 관형절이 곧 구체화 |
| R10 위반 위험 (관형절을 문두로 빼면 목적어-서술어 거리 발생) | 관형절이 피수식 명사 바로 앞에 오는 한국어 어순을 그대로 활용해 거리 0 |

한국어는 관형절이 피수식 명사 바로 앞에 오는 어순이 고정이라, 이 형태는
Garden path(R10)에도 걸리지 않는다 — R10과 R10-1을 동시에 해결하는 것이
이 기법의 핵심이다.

**점검 방법**: `OO을/를 (구조|시스템|파이프라인|아키텍처)(로|으로)\s?(설계|구축|구현)`
패턴이 나오면 OO이 명사형 동작어인지 확인한다. 맞으면 OO을 관형절 동사로
내리고 구조/시스템 등을 목적어로 승격한다.

## 2. 경력기술서 전용 규칙

### C1. 개조식 명사형 종결 — 앞선 문서의 "명사화 회피" 규칙은 여기서 반대로 적용

일반 한국어 문체 가이드는 명사화를 피하라고 하지만, **경력기술서는 명사형 종결이 규범**이다.

```
✅ 결제 모듈 리팩터링 및 배포 자동화 파이프라인 구축
❌ 결제 모듈을 리팩터링하면서 배포 자동화 파이프라인을 구축했습니다
```

- 한 항목 = 한 성과. 문장을 이어붙이지 않는다.
- 종결어미(`~했습니다`, `~함`)를 섞지 않는다. 문서 전체에서 하나로 통일.
- `~함`, `~됨` 체와 명사형 종결도 섞지 않는다. 명사형 종결 권장.

### C2. STAR 압축 구조

각 항목은 다음 순서로 압축한다.

```
[문제/맥락] → [행동/기술] → [결과/수치]
```

**예시**
```
- 주문 조회 API p95 응답 1.2s 병목 해소
  · 복합 인덱스 재설계 및 N+1 쿼리 제거 (JPA fetch join 적용)
  · p95 320ms 달성, DB CPU 사용률 68% → 31%
```

### C3. 계층 구조

```
회사명 | 직무 | 재직기간
  프로젝트명 (기간, 팀 규모)
    - 성과 항목 1
      · 세부 구현
      · 결과 수치
    - 성과 항목 2
  기술 스택: Java 17, Spring Boot 3, PostgreSQL, Redis, AWS ECS
```

- 성과 항목은 프로젝트당 2~4개. 5개 이상이면 중요도 낮은 것을 병합한다.
- 기술 스택은 나열만 하지 말고 어디에 썼는지 성과 항목에서 드러나게 한다.

### C4. 금지 사항

- 완결 문장 종결 (`~했습니다`)
- 감정·포부 표현 ("보람을 느꼈습니다", "성장했습니다")
- 지원 동기
- 팀 성과와 개인 기여의 구분 없는 서술 → 반드시 본인 역할 명시

## 3. 자기소개서 전용 규칙

### S1. 서술형 문장 — 합쇼체 통일

```
✅ 사내 정산 시스템의 마감 지연 문제를 맡아 배치 구조를 재설계했습니다.
❌ 사내 정산 시스템 마감 지연 문제 해결 및 배치 구조 재설계
```

- `~습니다`체로 통일. `~다`체(음슴체) 혼용 금지.
- 구어체(`~인데요`, `~거든요`) 금지.

### S2. 주어 최소화

한국어는 주어를 생략하는 것이 자연스럽다. "저는"을 문단마다 반복하면 유아적으로 읽힌다.

- 문단당 최대 1회, 논지 전환이 필요할 때만 사용
- 나머지는 생략하거나 행위 중심으로 서술

| ❌ | ✅ |
|---|---|
| 저는 문제를 발견했고, 저는 원인을 분석했으며, 저는 해결했습니다. | 배치 지연의 원인이 락 경합임을 확인하고, 파티션 단위 처리로 전환해 마감 시간을 4시간 단축했습니다. |

### S3. 두괄식 문단 구성

각 문단은 **결론 → 근거 → 의미** 순으로 쓴다. 서사적 도입("어릴 적부터~")은 배제한다.

```
[1문장] 무엇을 했고 무엇을 얻었는가 (결론)
[2~3문장] 어떤 상황에서 어떤 판단으로 (근거)
[1문장] 그래서 어떤 역량이 생겼는가 (의미)
```

**문항당 400~600자**를 기본으로 하되, 요구 분량이 있으면 그에 맞춘다.

### S4. 무생물 주어 — 성과 지표에는 오히려 자연스럽다

일반 번역 가이드는 무생물 주어를 사람 주어로 바꾸라고 하지만, **지표·시스템이 주어인 문장은 자기소개서에서 자연스럽다**.

```
✅ 이 개선으로 월간 장애 건수가 12건에서 2건으로 줄었습니다.
✅ 배치 구조 전환은 정산 마감 시간을 4시간 단축시켰습니다.
```

단, **행동 주체를 서술할 때는** 반드시 사람 중심으로 쓴다.
```
❌ 코드 리뷰 문화가 팀에 도입되었습니다.
✅ 주 2회 코드 리뷰 세션을 제안해 팀에 정착시켰습니다.
```

### S5. 회사·직무 연결 필수

마지막 문단은 반드시 지원 직무와 연결한다. 다만 아첨·미사여구는 배제하고 **역량-요구사항 매칭**으로 쓴다.

| ❌ | ✅ |
|---|---|
| 귀사의 무한한 발전에 이바지하고 싶습니다 | 대용량 결제 트랜잭션 처리 경험을 ○○의 정산 시스템 안정화에 적용할 수 있습니다 |

### S6. 금지 사항

- 상투적 도입 ("어릴 적부터", "저는 ○○한 사람입니다")
- 추상적 형용 ("열정적인", "성실한", "책임감 있는") — 반드시 행동 근거로 대체
- 회사 홈페이지 문구 복사
- 개조식 명사 종결 혼입

## 4. 린트 패턴 (후처리 검사용)

생성 후 별도 패스로 검사한다. 정규식으로 1차 필터링 후 LLM 검수를 권장한다.

### 4.1 공통 금지 패턴

```regex
# 이중 피동 / 수동태
/되어지|지게\s?되었|어지게|에\s?의해/

# 헤징
/것\s?같습니다|생각됩니다|한\s?편입니다|나름|조금이나마|어느\s?정도|다소/

# 번역체
/을\s?가지고\s?있|를\s?보유하고\s?있|에\s?대하여|에\s?관하여|중의\s?하나|필요로\s?하/

# 무색 동사
/진행하였|수행하였|담당하였|참여하였/

# 모호 지시어
/해당\s|이러한\s|그것은|상기\s|동\s?프로젝트/

# 정량화 누락 신호
/대규모|다양한|많은|여러|크게\s?개선|상당히|매우/
```

### 4.1-b 문장 구조 패턴 (R4-1, R8~R10, R10-1 대응)

정규식만으로는 오탐이 많다. **1차 후보 탐지용**으로만 쓰고 판정은 LLM에 맡긴다.

```regex
# R8: 무생물 주어 + 능동 타동사 (주어-서술어 불일치 후보)
/(은|는)\s.{0,25}(분리해|나눠|쪼개|처리해|구성해|적용해|연결해|묶어),/

# R8: 한 절에 피동+능동 혼재
/(되지|지지|이지)\s?않(게|도록).{0,15}(해|하여),/

# R9: 쉼표 연결 2회 이상
/[가-힣]+(해|여|하며|으며),.*?[가-힣]+(해|여|하며|으며),/

# R9: 문장 길이 초과 (자기소개서 기준 80자)
/[^.!?\n]{80,}[.!?]/

# R10: 목적어-서술어 거리 과다 (을/를 이후 10어절 이상)
/(을|를)\s(\S+\s){10,}\S+(했습니다|합니다|입니다)/

# R4-1: "하나가/이것이" 등으로 지칭 후 다른 명사로 재지칭 (후보)
/(하나|이것|그것)(가|이).{0,20}(해도|하면|이면).{0,20}그\s[가-힣]+(만|는|은|이|가)/

# R10-1: 동작 명사 목적어 + 구조/시스템 결합 (후보)
/[가-힣]+(을|를)\s(비동기|이벤트\s?기반|병렬|분산)?\s?(구조|시스템|파이프라인|아키텍처)(로|으로)\s?(설계|구축|구현)/
```

**LLM 검수 프롬프트 (구조 판정용)**

정규식에 걸린 문장을 아래 프롬프트로 넘긴다. 이 검사는 규칙 위반 여부보다
**판독 부하**를 보는 것이라 LLM 판정이 훨씬 정확하다.

```
다음 문장의 각 절을 나누고, 절마다 숨은 주어(생략된 주어 포함)를 표기하라.

문장: {sentence}

출력 형식:
- 절1: "..." → 숨은 주어: ...
- 절2: "..." → 숨은 주어: ...
판정: 서로 다른 주어가 2개 이하이면 PASS, 3개 이상이면 FAIL
FAIL인 경우 다음 두 방식 중 하나로 재작성하라.
  A) 주어를 행위자(나)로 통일하고 사물은 목적어로 내린다
  B) 사물을 주어로 두되 모든 서술어를 상태·피동으로 통일한다
원문의 기술적 사실은 하나도 빠뜨리지 말 것.
```

### 4.2 경력기술서 전용

```regex
# 완결 문장 혼입 (개조식 위반)
/(했습니다|합니다|입니다|였습니다)\s*$/m

# 감정·포부 표현
/보람|성장할\s?수|배울\s?수\s?있었|열정/
```

### 4.3 자기소개서 전용

```regex
# 개조식 혼입 (서술형 위반)
/(구축|개선|도입|담당|수행|적용|운영)\s*$/m

# 상투 도입
/어릴\s?적부터|어려서부터|저는\s?.{0,10}한\s?사람입니다/

# 추상 형용사 (행동 근거 없이 단독 사용 시)
/열정적인|성실한|책임감\s?있는|긍정적인|적극적인/

# 주어 과다 (문단 내 "저는" 2회 이상)
→ 정규식 대신 카운트 로직 권장
```

### 4.4 형식 검사

```regex
# 날짜 형식 위반
/\d{1,2}\/\d{1,2}\/\d{4}|\d{4}-\d{2}-\d{2}/   → 2024.03 형식으로 통일

# 천 단위 콤마 누락
/\d{5,}/   → 검토 대상
```

## 5. 에이전트 프롬프트 구성 권장안

규칙을 한 번에 다 넣으면 준수율이 떨어진다. **생성과 검수를 분리**한다.

### 5.1 생성 단계 — 문서 유형별로 규칙을 분기해서 주입

**경력기술서 프롬프트 (핵심 6개만)**
```
1. 개조식 명사형 종결로 통일 ("~ 구축", "~ 개선"). 완결 문장 금지.
2. 능동 표현. 수동태·이중피동 금지.
3. 모든 성과에 정량 지표. 없으면 규모·기간·범위로 대체.
4. [문제 → 행동/기술 → 결과] 순서.
5. "진행/수행/담당" 대신 구체 동사.
6. 팀 성과와 본인 기여를 구분해 명시.
```

**자기소개서 프롬프트 (핵심 8개)**
```
1. 합쇼체 완결 문장으로 통일. 개조식 금지.
2. 두괄식: 결론 → 근거 → 의미.
3. "저는"은 문단당 최대 1회.
4. 추상 형용사("열정적인") 금지, 행동과 결과로 대체.
5. "것 같습니다" 등 헤징 금지.
6. 마지막 문단은 지원 직무 요구사항과 역량을 직접 연결.
7. 한 문장 안에서 숨은 주어를 바꾸지 말 것. 사물이 주어면 서술어를 상태로
   ("~로 분리되어 있습니다"), 행동을 쓰려면 사물을 목적어로 내릴 것
   ("~를 분리했습니다"). 한 문장에 둘을 섞지 말 것.
8. 쉼표 연결("~해,")은 한 문장에 1회까지. 한 문장 60자 내외로 끊을 것.
```

> 7번은 기술 경험을 서술할 때 특히 자주 위반된다. 시스템 구조를 설명하는
> 문단에서는 프롬프트에 "이 문단은 방식 A(행위자 주어) / 방식 B(사물 주어
> 상태 서술) 중 하나로 통일하라"를 명시적으로 지정하는 편이 안정적이다.

### 5.2 검수 단계 — 별도 패스

```
입력: 생성된 텍스트 + 문서 유형
1) 정규식 린트 → 위반 위치 수집
2) LLM 검수 프롬프트에 위반 목록 전달 → 해당 부분만 수정
3) 재검사 (최대 2회 루프)
```

문장 전체 재생성보다 **위반 구간만 수정**하게 하는 편이 원문 정보 손실이 적다.

### 5.3 입력 데이터 스키마 제안

에이전트가 헤징이나 추상 표현을 만들어내는 원인은 대개 **입력 데이터에 수치가 없기 때문**이다. 수집 단계에서 강제하는 편이 낫다.

```json
{
  "company": "string",
  "period": { "start": "YYYY.MM", "end": "YYYY.MM | 현재" },
  "role": "string",
  "projects": [{
    "name": "string",
    "team_size": "number",
    "problem": "string",
    "actions": ["string"],
    "metrics": [{ "name": "string", "before": "string", "after": "string" }],
    "stack": ["string"],
    "my_contribution": "string"
  }]
}
```

`metrics`가 비어 있으면 에이전트가 생성 전에 사용자에게 되묻도록 설계한다.

```
  · Redis 기반 가맹점 정보 캐시 레이어 도입 (TTL 5분)
  · p95 응답시간 1.2s → 320ms, DB CPU 사용률 68% → 31%
  · 담당: 캐시 레이어 설계·구현 전담, 인덱스 재설계 리드
```

### 기술 구조 서술 (R8 위반 사례)

LLM이 생성한 실제 문장. 문법 오류는 없으나 한국어 화자가 어색함을 느끼는 전형.

**Before**
```
이미지 변환을 여러 워커 프로세스가 대기열에서 꺼내 처리하는 비동기 구조로
설계했습니다. 작업은 개별 단위로 나눠, 실패하면 그 단위만 재시도합니다.
엔진은 특정 업무에 묶이지 않게 분리해, 소스 획득 방식(압축파일·단일파일·원격)이
달라져도 같은 구조를 재사용합니다.
```

**진단**
| 문제 | 해당 규칙 |
|---|---|
| 1문장: `이미지 변환을`이 문미 `설계했습니다`까지 12어절 떨어져 있음 | R10 |
| 1문장: 동작 명사 `이미지 변환`이 `구조로 설계했다`의 목적어 자리에 옴 | R10-1 |
| 2문장: 숨은 주어 3개 (나 → 작업 → 시스템) | R8 |
| 3문장: 숨은 주어 4개 (나 → 엔진 → 소스 획득 방식 → 나) | R8 |
| 3문장: `묶이지 않게`(피동) + `분리해`(능동) 혼재 | R8 |
| 2·3문장 모두 `-해,` `-눠,` 동일 리듬 반복 | R9 |
| 괄호 삽입으로 문장 흐름 단절 | R9 |

**After — 방식 A (행위자 주어로 통일, R10-1 적용)**
```
여러 워커가 대기열에서 작업을 꺼내 변환하는 비동기 구조를 설계했습니다.
작업을 개별 단위로 쪼개 두어 실패한 단위만 다시 처리하면 됩니다.
변환 엔진은 특정 업무에 종속되지 않도록 분리했기 때문에, 소스를
압축파일·단일파일·원격 중 어디서 가져오든 같은 엔진을 그대로 씁니다.
```

**After — 방식 B (사물 주어 + 상태 서술로 통일)**
```
이미지 변환은 여러 워커 프로세스가 대기열에서 꺼내 처리하는 비동기 구조입니다.
작업은 개별 단위로 쪼개져 있어, 실패한 단위만 다시 처리됩니다.
변환 엔진은 특정 업무와 분리되어 있어, 소스 획득 방식이 압축파일이든
단일파일이든 원격이든 같은 구조로 동작합니다.
```

**After — 경력기술서(개조식)**
```
- 이미지 변환 비동기 처리 구조 설계
  · 워커 프로세스가 대기열에서 작업을 소비하는 큐 기반 구조 도입
  · 작업을 개별 단위로 분할해 실패 단위만 선택적으로 재시도
  · 변환 엔진을 업무 로직과 분리, 소스 획득 방식(압축파일·단일파일·원격)에
    관계없이 동일 엔진 재사용
```

> 개조식은 주어가 아예 생략되므로 R8 문제가 구조적으로 발생하지 않는다.
> 기술 구조 서술은 경력기술서에 두는 편이 안전하고, 자기소개서에서는
> "왜 그렇게 설계했는가"와 "그래서 무엇이 좋아졌는가"를 다루는 편이 낫다.
